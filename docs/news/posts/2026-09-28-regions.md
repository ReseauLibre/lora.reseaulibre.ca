Ça bouge sur le mesh, encore!

Une nouvelle [proposition de MeshCore Canada a été publiée](https://meshcore.ca/proposals/onqc-scopes/#phase-1-repeater-setup). Nous
pensons que tous les relais de la province devraient l'adopter pour
réduire le bruit entre les régions. Il s'agit d'une proposition en
plusieurs phases qui, au départ, n'aura pas d'impact significatif sur
les usagers à part pour le traffic entre les régions, puisqu'il risque
de séparer Québec de Montréal, à moins qu'une région soit assignée au
canal de communication.

Ottawa a déjà commencé à déployer ceci et s'est *déjà* séparé du mesh
de Montréal avec ce mécanisme.

Pour un relais dans la grande région de Montréal, prière d'appliquer
la configuration suivante:

```
region def yul|* qc|* onqc|* can|* na
region allowf *
region default yul
region save
```

D'autres configurations ont requises pour des relais à Québec, ainsi
que les relais limitrophes entre deux régions.

Voir plus bas pour d'autres exemples et explications!

<!-- more -->

## Choisir la bonne configuration

Les régions peuvent être complexes, mais la décision est assez
simple. Il s'agit de répondre à ces quelques questions:

 1. dans quelle [région Meshmapper](https://meshmapper.net/) se trouve le relais? (pour la
    grande région de Montréal, par exemple, il s'agit de [`yul`](https://yul.meshmapper.net/),
    pour Québec, c'est [`yqb`](https://yqb.meshmapper.net/))
 2. est-ce que le relais route des messages de d'autres régions? (pour
    un relais à Shawinigan connectant `yul` et `yqb`, ou le relais
    [`YQB-Belair`](https://yqb.meshmapper.net/?repeater=611E2E%2C46.82333%2C-71.49406&preset=all) à Québec, la réponse est oui!)
 3. si oui, est-ce que le relais doit router des messages de
    *d'autres* régions (par exemple, un relais à Trois-Rivières voudra
    probablement relayer les messages de `yul` et `yqb`)

La [Phase 1: repeater setup](https://meshcore.ca/proposals/onqc-scopes/#phase-1-repeater-setup) de la [proposition MeshCore Canada](https://meshcore.ca/proposals/onqc-scopes/#phase-1-repeater-setup)
vous guide assez bien au travers de toutes ces étapes, mais nous
allons faire un résumé avec quelques exemples ici.

On assume ici un relais roulant MeshCore 1.16 ou plus. Sinon, suivre
la [proposition](https://meshcore.ca/proposals/onqc-scopes/#phase-1-repeater-setup) qui a quelques exemples pour des versions plus
anciennes.

Ce guide assume également que vous n'avez aucune région déjà
configurée. Vous pouvez le vérifier en roulant la commande `region`,
qui devrait seulement retourner `*^ F`:

```
> region
*^ F
```

### Relais de ville à Montréal

Voici la configuration la plus simple, donnée comme exemple en
introduction ci-haut, pour un répéteur dans une ville comme Montréal:

```
region def yul|* qc|* onqc|* can|* na
region allowf *
region default yul
region save
```

Ceci fait les 4 chose suivantes

1. configuration du relais pour les messages des régions locales
   (`yul`), la province (`qc`), le corridor Ontario-Québec
   (`onqc`), et le reste du Canada (`can`) ainsi que l'amérique du
   nord (`na`)

2. tout de même permettre le trafic sans région (`allowf *`)
3. envoyer des annonces avec la région locale (`default yul`)
4. enregistrer la configuration

### Répéteur de ville à Québec

Même chose, mais dans la ville de Québec:

```
region def yqb|* qc|* onqc|* can|* na
region allowf *
region default yqb
region save
```

Voir ci-haut pour une explication: la seule différence est qu'on
configure le relais pour `yqb` plutôt que `yul`.

C'est la configuration qui devrait être initialement déployée sur 
[`YQB-Belair`](https://yqb.meshmapper.net/?repeater=611E2E%2C46.82333%2C-71.49406&preset=all) pendant que les gens commencent à utiliser les
régions avec leurs compagnons dans la ville de Québec.

### Relais en bordure de Québec

Voici la configuration qui devrait *éventuellement* être déployée sur
un relais comme [`YQB-Belair`](https://yqb.meshmapper.net/?repeater=611E2E%2C46.82333%2C-71.49406&preset=all):

```
region def yqb|* qc|* onqc|* can|* na
region denyf *
region default yqb
region save
```

*Éventuellement* ici, car nous comprenons que  `YQB-Belair` est un
relais clé dans la région. La configuration `denyf *` empêcherait au
relais de transmettre les messages sans région, ce qui pourrait être
très perturbant.

Donc, pour l'instant, commençons avec  `allowf *` jusqu'à ce que les
régions soient adoptées plus largement.

### Shawinigan edge repeater

Tout comme le relais limitrophe ci-haut, il serait peut-être mieux de
commencer avec une configuration  `allowf *` qui permettrait de
transmettre les messages sans région. Mais ultimement, un relais entre
les régions `yul` et `yqb` devrait avoir cette configuration:

```
region def yul|* yqb|* qc|* onqc|* can|* na
region denyf *
region default yqb
region save
```

La seule différence avec le relais de Québec est l'ajout de la région
`yul` ce qui signifie que le relais va passer les messages des *deux*
régions, `yul` et `yqb`.

Notez que nous assumons ici que le relais se considère comme faisant
partie de la région `yqb`, mais s'il se considèrerait dans la région
`yul`, la seule différence serait de changer la ligne `default` qui
serait alors:

```
region default yul
```

Et encore une fois, ceci est une configuration un bring agressive qui
pourrait être perturbante. Il est mieux de commencer avec `allowf *`
et basculer lorsque les compagnons ont adopté les régions.

### Compagnons

Pour l'instant, rien ne change pour les compagnons. Tous (ou presque!)
les relais dans une région doivent configurer les régions avant que
les compagnons puissent les utiliser car un relais non-configuré va
simplement **ignorer les paquets avec régions**!

La  [phase 2](https://meshcore.ca/proposals/onqc-scopes/#phase-2-companion-setup) de la proposition est présentemnent prévue pour
Janvier 2027, mais il est possible qu'on doive faire ces changements
plus tôt si nous avons toujours des problèmes de flood.

En phase 2, les compagnons commencent à régler une régions par défaut
(utilisée pour les DMs) et régler une région pour chaque canal (que
nous documenterons dans notre [list des canaux](../../guides/meshcore/channels.md)).

## Why?

This is solving a similar issue than the [floods and loops
proposal](2026-09-20-limit-flood-and-loops.md) in that we're trying to limit the amount of traffic key
repeaters need to carry.

Regions have already been deployed in Ottawa, which has effectively
split the network unless we start scoping packets. So if we want to
resume cross-regions communications, we *must* start using regions.

Setting up regions will also allow people to get more familiar with
this tool: in some circumstances (for example, a remote village), it
might be a useful mechanism to allow a community to talk locally
without sending their messages across the entire mesh.

## Questions?

### What's phase 3?

> There's a phase 1 and phase 2, what's phase 3?

[Phase 3](https://meshcore.ca/proposals/onqc-scopes/#phase-3-only-if-needed) is a last resort mechanism that we can use in a noisy
city to limit hop counts for unscoped packets. This would be done
with:

    set flood.max.unscoped 3

It's a softer version than `denyf *` in that it still relays traffic
for a few hops, but then stops.

### Can I add more regions in there?

> Can I add, say `YUL`, `Yul` or `YOLO` to the regions list in case
> people misspell?

Please don't! There are regions discovery mechanisms in MeshCore that
make companions discover regions. Adding those extra regions will just
confuse everyone and bring ambiguity as to what should actually be in
use.
